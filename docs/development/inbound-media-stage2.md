# 微信入站媒体第二步：绑定取件与私有暂存

2026-09-27；关联 Issue #13、PR #14。在第一步响应契约之上增加实际 HTTP 取件和 Linux 私有缓存发布。本步骤仍未接入生产 Poll/Dispatch，没有部署、没有重试历史 dead 任务，不代表微信附件闭环已修复。

## 宿主与容器

CFserver 宿主保持 Debian13。微信镜像的 Ubuntu22.04 基础用户环境不是宿主发行版，未要求更换系统；镜像标签22.04也不是已核实的 agent-server 应用版本。宿主/容器差异不是已经定位的空正文图片错误原因。

## 新增行为

`InboundMediaHTTPClient.fetch` / `fetch_async` 提供真正的媒体 GET 路径。配置端点和凭据由操作者给出，MediaSource 必须来自已经持久化并通过身份/会话准入的消息，不提供给模型任意填写。

一次取件最多执行固定五次 GET：当前微信认证、该会话消息列表、指定消息媒体，再复核认证和同一条消息。绑定账号、会话、发送者、local/server ID、消息类型、UTC时间和正文摘要。纯图片正文为空合法，但身份字段仍须匹配；不以占位文字代替附件。消息不在可见窗口、不唯一、ID复用/内容变化、账号切换等拒绝继续。前后检查不等于证明微信内部缓存实现或排除所有瞬时切换。

响应流在JSON解析前限制总大小，Base64解码继续复用第一步上限；请求有整体deadline，持续慢速返回也不能无限占用。拒绝重定向、非JSON、压缩编码、异常Content-Length、重复JSON键、非有限JSON值和媒体类型不符。固定端点内部HTTP复用现有Docker网络边界；HTTPS沿用标准证书验证，不新增跳过校验开关。环境代理不参与。

pending/unsupported 原样分类，HTTP408/425/429/5xx/传输中断标记可由外层安排等待，凭据/来源/格式错误不标记可重试。取件器本身不循环重试，也不调用Hermes。pending不证明原生下载已排队。媒体GET可能触发微信内部缓存副作用。

`InboundMediaStaging.publish` 将已经通过绑定的字节保存到预配置的私有暂存根：Linux dirfd/no-follow路径遍历、根目录必须当前身份所有且0700、文件0600、独占临时文件和no-replace发布、文件/目录fsync、重新读取校验；使用来源指纹和内容摘要命名，不使用原文件名作为本地路径。元数据发布失败保留已写blob，不返回成功。显式再次处理相同来源/内容会先核验再复用，变更内容/权限/链接拒绝覆盖。不同图片版本单独保存，比较状态不变；预览字节不会被宣称为原图。

暂存是受控附件缓存，不是第二个正式文件服务，也不是已经可投递的Gateway READY Artifact。正式入库仍走FileBrowser API；Hermes是否能访问这份引用仍需后续交接契约。暂存文件不自动打开/执行，不清理唯一产物。

## 测试范围与限制

新增66个本地参数化测试通过，Python3.13.5和当前HTTPX。测试包括真实回环HTTP服务 → 五次绑定取件 → 临时目录no-replace落盘 → 实际字节比对，以及模拟HTTP错误、流超限、总超时、账号/消息变化、空正文图片、等待状态不落盘、版本区别、文件篡改、权限/软硬链接拒绝、元数据发布故障后的显式恢复。只使用合成字节和临时目录，无生产文件和凭据。

本地网络DNS不可用，无法clone完整仓库或安装Ruff；从连接器固定提交取得第一步依赖并校验Git blob，新增组件在局部工作目录独立测试。完整包导入、目标Python3.12和全仓库测试以精确提交的GitHub CI为准。本地66通过不等于全仓库、TLS实机、PDF格式解析、掉电硬件或正式归档验收。

## 尚待接通

持久数据库取件队列及过期/退避策略、Poll事务中的准入和排队、媒体与同线程文本的FIFO、持久登记与生命周期清理、Hermes工具/多模态交接、失败用户通知、FileBrowser归档和真实微信回传尚未完成。本步骤不改生产空正文guard或原get_media接口，不能把添加模块说成现场图片已经恢复。

PDF持续pending与现场微信镜像原生下载能力仍单独未解决；代码不能让上游凭空返回原件。现有样本、失败记录和登录状态均保留，不能靠删队列、盲升级镜像或重新发送伪造本次成功。
